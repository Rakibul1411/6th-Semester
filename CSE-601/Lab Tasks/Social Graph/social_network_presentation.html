Scaling Architecture Overview

🏗️ Distributed System Architecture

This diagram illustrates how our social network scales from a single-server solution to a distributed, load-balanced system capable of handling billions of connections across multiple Person Servers.

Scaling Strategy & Implementation

📈 Horizontal Scale (Add More Workers Behind LB)

  • Web Server (reverse proxy): Stateless, just add more
  • Query API: Stateless orchestration, scale out
  • User Graph Service: Stateless compute (BFS), scale out
  • Lookup Service: Service instances scale out; all serve the same shard map
  • Load Balancer: Multiple instances/managed pairs for High Availability

🔀 Sharding (Split Data by Key)

  • Person Servers: Primary sharding by person_id via consistent hashing/modulo
  • Memory Cache: Keys sharded across cache nodes (consistent hashing)

🔄 Replication (Extra Copies for HA/Read Scale)

  • Person Servers: Each shard has 1 primary + N read replicas
  • Memory Cache: Redis/Memcached clusters with replicas for failover

Performance Optimizations

🚀 Caching Strategies

  • Memory Cache: Store complete/partial BFS traversals
  • NoSQL Database: Batch compute offline BFS results

⚡ Algorithm Improvements

  • Bidirectional BFS: Search from both source and destination
  • High-degree Node Priority: Start from users with many friends
  • Batch Processing: Group lookups by server location

🌍 Infrastructure Optimizations

  • Geographic Sharding: Leverage friend locality
  • Search Limits: Time/hop-based query boundaries
  • Graph Databases: Neo4j or GraphQL for specialized queries

Most Impactful: Bidirectional BFS can reduce search time exponentially by meeting in the middle.

🛡️ Protection Measures

  • Authentication and Authorization: Verify user identity and ensure users can only see allowed data.
  • Data Privacy: Protect user friend lists and profiles from unauthorized access.
  • Encryption: Use HTTPS for client-server communication.
  • Rate Limiting: Prevent abuse and denial-of-service attacks.
  • Audit Logging: Track who accesses what data and when.
  • Input Validation and Sanitization: Prevent injection attacks or malformed queries.
  • Service Isolation: Run components in isolated environments (microservices or containers).

Design Trade-offs & Lessons Learned

⚖️ Key Trade-offs

Complexity vs Performance
Distributed BFS is complex but necessary for scale
Latency vs Consistency
Caching improves speed but may serve stale data
Precomputation vs Storage
Faster searches require more storage space

📚 Critical Lessons

  • Lookup Services: Must be highly available and replicated
  • Caching is Essential: Hot queries need immediate response
  • Bidirectional BFS: Single most impactful optimization
  • Sharding Strategy: Geographic clustering improves performance
  • Balance is Key: Optimize accuracy, speed, and cost together
